## Rutina de trabajo

Repite esto cada vez que te sientes a trabajar y cada vez que termines un paso.

**Al empezar la sesión**

```powershell
cd C:\ruta\a\rag-lab
git switch v0.1-baseline      # la rama de esta versión (se crea en el paso 0)
git pull                      # por si cambiaste algo desde otro ordenador
git status                    # debe decir "working tree clean"
```

**Antes de cada commit**, los tres controles de calidad:

```powershell
uv run ruff format .          # formatea el código
uv run ruff check .           # busca errores y malas prácticas
uv run pytest                 # ejecuta los tests
```

Si `ruff check` se queja, muchas veces lo arregla solo con `uv run ruff check . --fix`.

**Commit y subida**

```powershell
git status                    # revisa QUÉ vas a subir
git add <archivos>            # o "git add ." si todo lo listado es tuyo y correcto
git commit -m "feat: descripción corta en inglés"
git push
```

Prefijos de commit: `feat:` (funcionalidad nueva), `test:` (tests), `fix:` (arreglo),
`docs:` (documentación), `eval:` (evaluación o resultados), `refactor:` (cambio sin efecto
visible), `chore:` (configuración, herramientas).

**Regla de oro**: antes de `git add`, lee la salida de `git status`. Nunca deben aparecer
`.env`, `index/` ni `.venv/`. Si aparecen, para y revisa el `.gitignore`.

## Paso 2. Escribir el dataset de evaluación

**Objetivo**: 20-30 preguntas escritas a mano, **antes** de escribir el pipeline.

Esto va antes que el código por una razón: si escribes las preguntas después de ver qué
recupera tu sistema, sin querer harás preguntas fáciles para él.

**Archivos**

- ✏️ `src/rag/models.py` (dos campos nuevos en `EvalCase`)
- ✏️ `data/eval/questions.jsonl`
- ✏️ `data/eval/README.md`

**Qué hacer**

1. **Mejora `EvalCase`**. Con pocos documentos, decir que un trozo es relevante solo porque
   viene del documento correcto infla las métricas, porque cada documento tiene muchos
   trozos. Así que añade un campo `gold_evidence`: una frase literal corta (5-15 palabras)
   copiada del documento, que debe aparecer en el trozo correcto. Añade también `tags`, que
   te servirá en el paso 12 para medir tipos de pregunta por separado.

   En `src/rag/models.py`, dentro de `EvalCase`, añade estos dos campos debajo de
   `expected_answer`:

   ```python
   gold_evidence: str | None = None  # short literal phrase copied from the source
   tags: list[str] = Field(default_factory=list)  # e.g. ["exact_term"], ["multi_hop"]
   ```

   `Field` ya está importado en ese archivo.

2. **Escribe las preguntas** en `data/eval/questions.jsonl`, borrando los tres ejemplos.
   Una pregunta por línea, en JSON y en una sola línea:

   ```json
   {"id": "q01", "question": "What status code does FastAPI return when request validation fails?", "answerable": true, "gold_doc": "fastapi_errors.md", "gold_section": null, "gold_evidence": "returns an HTTP 422 error", "expected_answer": "422 Unprocessable Entity", "tags": ["exact_term"]}
   ```

   Reparte así las 20-30 preguntas:

   | Tipo | Cuántas | Tag | Ejemplo |
   |---|---|---|---|
   | Hecho directo | 10-15 | `factual` | "What does X default to?" |
   | Término exacto, código, sigla o nombre | 4-6 | `exact_term` | "What is error E1042?" |
   | Necesita unir dos partes | 2-4 | `multi_hop` | "Which of A or B supports C?" |
   | Sin respuesta en el corpus | 3-5 | `unanswerable` | Algo plausible que no aparece |

   Reglas para que el dataset sea bueno:
   - Formula las preguntas **con tus palabras**, no copiando frases del documento, porque en
     la vida real el usuario no conoce el texto exacto.
   - `gold_evidence` sí debe ser **literal**: cópiala y pégala del documento.
   - Para las preguntas sin respuesta pon `"answerable": false` y deja a `null` `gold_doc`,
     `gold_evidence` y `expected_answer`.
   - `expected_answer` corta: una cifra, un nombre o una frase.

3. **Actualiza `data/eval/README.md`**: añade las filas de `gold_evidence` y `tags` a la
   tabla de campos, y la tabla de tipos de pregunta de arriba.

**Comprobación**


El test `test_eval_dataset_parses` carga cada línea con `EvalCase`. Si una línea está mal

## Paso 3. Cargar documentos

**Objetivo**: convertir cada archivo en una lista de `RawPage` (texto + página).

**Archivos**

- ✏️ `src/rag/ingest/loaders.py` (función `load_document`)
- ➕ `tests/test_loaders.py`

**Qué hacer**

Implementa `load_document(path)` con tres ramas según `path.suffix.lower()`:

- **`.pdf`**: usa `pypdf`. Una `RawPage` por página, con `page` empezando en 1:

  ```python
  from pypdf import PdfReader

  reader = PdfReader(path)
  for number, pdf_page in enumerate(reader.pages, start=1):
      text = pdf_page.extract_text() or ""
      # create RawPage(doc=path.name, page=number, text=text)
  ```

  `extract_text()` puede devolver `None` en páginas vacías o escaneadas, y por eso el
  `or ""`. Omite las páginas cuyo texto quede vacío tras `.strip()`.

- **`.md` y `.txt`**: `path.read_text(encoding="utf-8")` y una sola `RawPage` con
  `page=None`.

- **Otra extensión**: `raise ValueError(f"Unsupported file type: {path.suffix}")`.

Detalles que importan:

- Usa `path.name` (por ejemplo `guide.pdf`) como `doc`, no la ruta completa: así los ids no
  dependen de dónde tengas la carpeta.
- Normaliza saltos de línea de Windows: `text.replace("\r\n", "\n")`. Si no, el chunking
  del paso 4 no detectará bien los párrafos.
- Los PDF suelen traer guiones de corte de línea ("retrie-\nval"). Para la v0.1 no hace
  falta arreglarlo, pero apúntalo como posible mejora si lo ves al leer los trozos.

**Tests** en `tests/test_loaders.py`. pytest te da `tmp_path`, una carpeta temporal:


Para el PDF no hace falta un test automático en la v0.1. Compruébalo a mano con uno de tus
documentos.

## Paso 4. Chunking

**Objetivo**: partir cada documento en trozos de ~500 tokens con ~75 tokens de solapamiento,
respetando los párrafos. Es la pieza que más afecta a la calidad, así que tómate tu tiempo.

**Archivos**

- ✏️ `src/rag/ingest/chunking.py` (función `chunk_pages` y funciones auxiliares)
- ✏️ `tests/test_chunking.py` (quitar los `@IMPLEMENT`)

**Conceptos antes de empezar**

- **Token**: el trozo de texto con el que trabajan los modelos (una palabra corta, o parte
  de una larga). Medir por tokens y no por caracteres hace que los tamaños sean comparables
  entre textos.
- **Solapamiento (overlap)**: los últimos tokens de un trozo se repiten al principio del
  siguiente. Así, si una idea queda partida en la frontera, está entera en al menos uno de
  los dos.

**Qué hacer**

1. **Cambia la firma** para recibir el hash del documento, porque `Chunk` lo necesita y
   `RawPage` no lo tiene. Llamarás a `chunk_pages` una vez por documento:

   ```python
   def chunk_pages(
       pages: list[RawPage], max_tokens: int, overlap: int, doc_hash: str = ""
   ) -> list[Chunk]:
   ```

2. **Funciones auxiliares** (arriba del archivo):

   ```python
   import re

   import tiktoken

   _ENC = tiktoken.get_encoding("cl100k_base")


   def count_tokens(text: str) -> int:
       return len(_ENC.encode(text))
   ```

   ⚠️ La primera vez que se ejecuta, tiktoken **descarga** su vocabulario de internet y luego
   lo guarda en caché. Si estás sin conexión o detrás de un proxy de empresa, fallará con un
   error de conexión: ejecútalo una vez con internet normal.

3. **El algoritmo**, en tres fases:

   **Fase A. Párrafos.** Divide el texto de cada página por líneas en blanco:
   `re.split(r"\n\s*\n", text)`, quita espacios con `.strip()` y descarta los vacíos.
   Luego **une los títulos al párrafo siguiente**: si un párrafo es muy corto (12 tokens o
   menos) y no termina en `.`, `:`, `?` o `!`, probablemente sea un título, así que
   guárdalo y pégalo delante del siguiente párrafo. Sin esto, un título acaba solo en un
   trozo propio, que no sirve para nada.

   **Fase B. Párrafos demasiado largos.** Si un párrafo tiene más de `max_tokens`, pártelo
   con una **ventana deslizante** sobre sus tokens:

   ```python
   def _windows(tokens: list[int], max_tokens: int, overlap: int) -> list[list[int]]:
       step = max_tokens - overlap
       out = []
       for start in range(0, len(tokens), step):
           out.append(tokens[start : start + max_tokens])
           if start + max_tokens >= len(tokens):
               break
       return out
   ```

   Cada ventana se convierte de nuevo en texto con `_ENC.decode(ventana)`.

   **Fase C. Empaquetar.** Recorre las piezas (párrafos o ventanas) y ve llenando un trozo:

   ```
   trozo_actual = [], tokens_actuales = 0
   para cada pieza:
       si trozo_actual no está vacío y tokens_actuales + tokens(pieza) > max_tokens:
           cerrar trozo_actual (unir sus piezas con "\n\n")
           cola = últimos `overlap` tokens del trozo cerrado
           empezar el nuevo trozo con la cola, si cabe junto a la pieza
       añadir la pieza al trozo_actual
   al final, cerrar lo que quede
   ```

4. **Construye cada `Chunk`**:
   - `id`: `f"{page.doc}::p{page.page or 0}::c{i:03d}"`, donde `i` es un contador que
     **no se reinicia entre páginas**. Ejemplo: `guide.pdf::p12::c041`. El `:03d` rellena
     con ceros para que los ids se ordenen bien.
   - `n_tokens`: `count_tokens(texto)`. **Nunca debe superar `max_tokens`**.
   - `doc_hash`: el parámetro que recibes.
   - `section`: déjalo en `None` en la v0.1.

5. **Valida los parámetros** al principio: si `overlap >= max_tokens`, lanza `ValueError`
   (la ventana no avanzaría nunca y el bucle sería infinito).

6. **Activa los tests**: en `tests/test_chunking.py`, borra las tres líneas `@IMPLEMENT`
   (y la definición de `IMPLEMENT` si `ruff` dice que ya no se usa).

**Comprobación**

```powershell

```

Después, **lee los trozos a ojo**. Es la comprobación más importante del paso:

## Paso 5. Embeddings

**Objetivo**: convertir textos en vectores normalizados con `BAAI/bge-small-en-v1.5`.

**Archivos**

- ✏️ `src/rag/embeddings.py` (clase `Embedder`)
- ➕ `tests/test_embeddings.py`

**Conceptos antes de empezar**

- Un **embedding** es una lista de números (aquí 384) que representa el significado de un
  texto. Textos con significado parecido dan vectores que apuntan en direcciones parecidas.
- **Normalizar** es escalar el vector para que mida 1. Con vectores normalizados, el
  producto escalar es igual a la similitud coseno, que es justo lo que usará el store.

**Qué hacer**

1. **Carga perezosa del modelo**, para que importar el paquete no tarde segundos:

   ```python
   def _get_model(self):
       if self._model is None:
           from sentence_transformers import SentenceTransformer

           self._model = SentenceTransformer(self.model_name)
       return self._model
   ```

   La primera vez descargará el modelo (unos 130 MB) en la caché de Hugging Face. Las
   siguientes, lo carga del disco.

2. **`encode_passages(texts)`**:

   ```python
   vectors = self._get_model().encode(
       texts, batch_size=32, normalize_embeddings=True, show_progress_bar=True
   )
   return np.asarray(vectors, dtype=np.float32)
   ```

3. **`encode_query(text)`**: los modelos `bge` recomiendan un prefijo para las preguntas
   (no para los trozos). Guárdalo como constante:

   ```python
   QUERY_PREFIX = "Represent this sentence for searching relevant passages: "
   ```

   y codifica `QUERY_PREFIX + text`, devolviendo el vector de una dimensión (`[0]` del
   resultado si codificas una lista de un elemento).

   Deja el prefijo configurable (por ejemplo, un parámetro `use_query_prefix: bool = True`
   en el constructor). Medir con y sin prefijo será tu primer experimento del paso 8.

**Tests** en `tests/test_embeddings.py`. Descargan el modelo, así que márcalos como lentos
para poder saltarlos:

```python
import numpy as np
import pytest

from rag.embeddings import Embedder

pytestmark = pytest.mark.slow


@pytest.fixture(scope="module")
def embedder():
    return Embedder("BAAI/bge-small-en-v1.5")


def test_shapes_and_normalisation(embedder):
    v = embedder.encode_passages(["first text", "second text"])
    assert v.shape == (2, 384)
    assert v.dtype == np.float32
    assert np.allclose(np.linalg.norm(v, axis=1), 1.0, atol=1e-4)


def test_similar_texts_are_closer(embedder):
    q = embedder.encode_query("How do I install the package?")
    p = embedder.encode_passages(["Run pip install to set it up.", "The sky is blue."])
    assert p[0] @ q > p[1] @ q
```

Registra el marcador `slow` en `pyproject.toml`, dentro de `[tool.pytest.ini_options]`:

```toml
markers = ["slow: tests that download or run models"]
```


## Paso 6. El store con numpy y SQLite

**Objetivo**: guardar vectores y trozos en disco, cargarlos y buscar los más parecidos.

**Archivos**

- ✏️ `src/rag/store/numpy_store.py`
- ✏️ `src/rag/store/base.py` (pequeño cambio en `save`)
- ✏️ `tests/test_store.py`

**Cómo encaja todo** (repaso de lo que decidimos):

```
index/vectors.npy   matriz float32 [n_trozos, 384]   fila i
index/chunks.db     tabla chunks                      row_idx = i
index/meta.json     modelo, tamaño de chunk, n_trozos, fecha, hashes
```

La fila `i` de la matriz y la fila con `row_idx = i` de la tabla son el mismo trozo.

**Qué hacer**

1. **`add(chunks, vectors)`**: comprueba que `len(chunks) == vectors.shape[0]` (si no,
   `ValueError` con un mensaje claro), convierte a `float32` y añade. Si ya había vectores,
   comprueba que la dimensión coincide y usa `np.vstack`.

2. **`search(query_vector, k)`**:

   ```python
   if self._vectors is None or len(self._chunks) == 0:
       return []
   scores = self._vectors @ query_vector.astype(np.float32)   # una puntuación por trozo
   k = min(k, len(self._chunks))
   top = np.argpartition(-scores, k - 1)[:k]     # los k mejores, sin ordenar
   top = top[np.argsort(-scores[top])]           # ordenados de mejor a peor
   ```

   Después, crea un `RetrievalResult` por índice con `rank` empezando en 1. Usa
   `float(scores[i])` para que pydantic reciba un `float` normal y no un tipo de numpy.

   `argpartition` encuentra los k mejores sin ordenar toda la lista, y luego solo ordenas
   esos k. Con miles de trozos no lo notarás, pero es la forma correcta.

3. **`save(directory, extra_meta=None)`**. Añade el parámetro `extra_meta: dict | None = None`
   también en `store/base.py`, para pasar el modelo de embeddings y los hashes de los
   documentos.

   El esquema de la tabla:

   ```python
   SCHEMA = """
   CREATE TABLE chunks (
       row_idx   INTEGER PRIMARY KEY,
       id        TEXT UNIQUE NOT NULL,
       doc       TEXT NOT NULL,
       page      INTEGER,
       section   TEXT,
       text      TEXT NOT NULL,
       n_tokens  INTEGER NOT NULL,
       doc_hash  TEXT NOT NULL
   )
   """
   ```

   El orden de guardado, pensado para que una interrupción no deje el índice a medias
   (limitación L5):

   1. `directory.mkdir(parents=True, exist_ok=True)`.
   2. Escribe todo en **archivos temporales**: `vectors.tmp.npy`, `chunks.tmp.db` y
      `meta.tmp.json`. Si `chunks.tmp.db` ya existe de un intento anterior, bórralo antes.
   3. Con todo escrito, **renómbralos** a sus nombres finales con `os.replace(origen, destino)`.

   ⚠️ Dos trampas:
   - `np.save` añade `.npy` si el nombre no termina en `.npy`. Por eso el temporal se llama
     `vectors.tmp.npy` y no `vectors.npy.tmp`.
   - En SQLite, usa `con.executemany("INSERT INTO chunks VALUES (?, ?, ?, ?, ?, ?, ?, ?)",
     filas)` y no construyas el SQL pegando textos: los trozos tienen comillas y romperían
     la consulta. Llama a `con.commit()` y cierra la conexión (en un bloque `try/finally`)
     **antes** de `os.replace`, porque en Windows no se puede renombrar un archivo abierto.

   El `meta.json` debe incluir como mínimo `n_chunks`, `dim`, `created_at` (con
   `datetime.now(UTC).isoformat()`) y lo que llegue en `extra_meta`.

4. **`load(directory)`**: lee `meta.json`, `np.load` de los vectores, y la tabla con
   `SELECT ... FROM chunks ORDER BY row_idx` (el `ORDER BY` es imprescindible). Reconstruye
   los `Chunk`. Si `len(chunks)`, `vectors.shape[0]` y `meta["n_chunks"]` no coinciden, lanza
   `RuntimeError("index is out of sync: rebuild it with `rag ingest`")`.

**Tests** en `tests/test_store.py`, añadidos a los dos que ya hay. Vectores aleatorios
normalizados, sin modelo:

```python
import numpy as np

from rag.models import Chunk


def _chunks(n):
    return [
        Chunk(id=f"a.md::p0::c{i:03d}", doc="a.md", text=f"t{i}", n_tokens=1, doc_hash="h")
        for i in range(n)
    ]


def _vectors(n, dim=8):
    v = np.random.default_rng(0).normal(size=(n, dim)).astype(np.float32)
    return v / np.linalg.norm(v, axis=1, keepdims=True)


def test_own_vector_ranks_first():
    store = NumpyStore()
    v = _vectors(50)
    store.add(_chunks(50), v)
    results = store.search(v[17], k=5)
    assert results[0].chunk.id == "a.md::p0::c017"
    assert [r.rank for r in results] == [1, 2, 3, 4, 5]


def test_save_and_load_round_trip(tmp_path):
    store = NumpyStore()
    v = _vectors(20)
    store.add(_chunks(20), v)
    store.save(tmp_path)
    loaded = NumpyStore()
    loaded.load(tmp_path)
    assert len(loaded) == 20
    assert loaded.search(v[3], k=1)[0].chunk.id == "a.md::p0::c003"
    assert not list(tmp_path.glob("*.tmp.*"))     # no temporary files left behind
```

## Paso 7. El comando `rag ingest`

**Objetivo**: un comando que construye el índice y no hace nada si nada ha cambiado.

**Archivos**: ✏️ `src/rag/cli.py` (comando `ingest`)

**Qué hacer**

1. Al principio del comando, carga la configuración: `settings = get_settings()` (de
   `rag.config`).
2. **Lista los documentos**: archivos de `path` cuya extensión sea `.pdf`, `.md` o `.txt`,
   **ordenados por nombre** (`sorted(...)`), para que el índice salga igual en cada ejecución.
3. **Calcula el hash** de cada uno con `file_sha256` y monta un diccionario
   `{nombre_archivo: hash}`.
4. **Decide si hay que reindexar**. Si existe `index/meta.json` y en él coinciden los hashes,
   el modelo de embeddings, `chunk_tokens` y `chunk_overlap`, imprime
   `"Index is up to date, nothing to do."` y termina. Si no, **reconstruye el índice
   entero**. Reindexar todo ante cualquier cambio es justo la limitación L4: dejarla así y
   medirla es parte del plan.
5. **Construye el índice**: para cada documento, `load_document`, luego `chunk_pages` con su
   hash. Junta todos los trozos y codifica sus textos de una sola vez con
   `embedder.encode_passages` (en lotes es mucho más rápido que uno a uno). Crea un
   `NumpyStore`, haz `add` y luego `save(settings.index_dir, extra_meta={...})` con el modelo,
   `chunk_tokens`, `chunk_overlap` y el diccionario de hashes.
6. **Informa** al final: número de documentos, de trozos y segundos que tardó (mide con
   `time.perf_counter()`). Ese tiempo lo necesitarás para L4.
7. Quita el `raise typer.Exit(code=1)` del final de `ingest`, que estaba solo porque el
   comando no hacía nada.

```powershell
Get-ChildItem index               # chunks.db, vectors.npy, meta.json

```

**Objetivo**: medir si encuentras el trozo correcto, **sin usar Claude todavía**.

**Qué hacer**

2. **`is_relevant(result, case)`**:

   ```python
   def load_cases(path: Path) -> list[EvalCase]: ...
   ```

   trozo correcto) y devuelve:

     tag es lo que te dirá en el paso 12 si las preguntas `exact_term` van peor.

   - `config`: `settings.model_dump(mode="json", exclude={"anthropic_api_key"})`.
     ⚠️ El `exclude` es imprescindible: **la clave de la API no puede acabar en un archivo

   - `metrics` y `per_question`.

## Paso 9. Generación con citas y `rag ask`

**Objetivo**: responder con Claude usando solo los trozos recuperados, citando sus ids.

A partir de aquí necesitas el `.env` con `ANTHROPIC_API_KEY` (ver el README).

**Archivos**

- ✏️ `src/rag/generation.py`
- ✏️ `src/rag/cli.py` (comando `ask`)
- ➕ `tests/test_generation.py`

**Qué hacer**

1. **`build_prompt(template, question, results)`**. Cada trozo en el contexto lleva su id
   delante, para que el modelo pueda citarlo:

   ```
   [guide.pdf::p12::c041]
   texto del trozo...

   [notes.md::p0::c003]
   texto del trozo...
   ```

   Rellena la plantilla con `template.format(context=contexto, question=question)`.
   ⚠️ Con `.format`, cualquier `{` o `}` **dentro de la plantilla** se interpreta como hueco.
   Si alguna vez escribes llaves literales en un prompt (por ejemplo, un JSON de ejemplo),
   escríbelas dobles: `{{` y `}}`. El texto de los trozos no da problemas, porque se inserta
   como valor.

2. **`generate_answer(...)`**. Añádele un parámetro `api_key` (o recibe `settings`):

   ```python
   import anthropic

   client = anthropic.Anthropic(api_key=api_key)
   response = client.messages.create(
       model=model,
       max_tokens=max_tokens,
       temperature=0,
       messages=[{"role": "user", "content": prompt}],
   )
   return response.content[0].text
   ```

   - `temperature=0` hace las respuestas lo más repetibles posible, que es lo que quieres para
     evaluar.
   - Pasa la clave explícitamente: pydantic-settings lee el `.env`, pero **no** lo convierte en
     variable de entorno, así que `anthropic.Anthropic()` sin argumentos no la encontraría.
   - Crea el cliente una sola vez si vas a hacer muchas llamadas (en el paso 10).

3. **`cited_ids(answer)`**: extrae las citas con una expresión regular:

   ```python
   CITATION_RE = re.compile(r"\[([^\[\]]+?::[^\[\]]+?)\]")
   return set(CITATION_RE.findall(answer))
   ```

4. **`citations_are_valid(answer, results)`**: `True` si cada id citado está entre los ids
   recuperados. Una respuesta sin citas: decide tú qué cuenta (yo la marcaría como no válida
   salvo que sea la frase de "no lo sé") y anótalo en `docs/decisions.md`.

5. **Añade `is_abstention(answer)`**: `True` si la respuesta contiene la frase exacta del
   prompt, `"I don't know based on the provided documents"`.

6. **`rag ask`**: carga store y embedder, recupera, genera, e imprime la respuesta y debajo
   las fuentes (id + primeros 100 caracteres de cada trozo citado). Quita el
   `raise typer.Exit(code=1)`.

**Tests** en `tests/test_generation.py`: `build_prompt`, `cited_ids`,
`citations_are_valid` e `is_abstention` son funciones puras, sin red, así que se testean
fácil con resultados inventados como en `test_metrics.py`. **No testees `generate_answer`
llamando a la API**: sería lento, costaría dinero y fallaría sin conexión.

## Paso 11. Análisis de fallos

**Objetivo**: saber **por qué** falla cada pregunta. Esta tabla vale más que cualquier métrica.

**Archivos**: ➕ `docs/failure_analysis_v0.1.md`

**Qué hacer**

Toma cada pregunta que falla en algo (Hit@5, corrección, fidelidad o abstención) y
clasifícala con una única causa principal:

| Causa | Cómo reconocerla |
|---|---|
| **Carga** | El texto extraído ya está roto (tabla deshecha, palabras pegadas) |
| **Chunking** | La respuesta está partida entre dos trozos, o el trozo mezcla temas |
| **Recuperación** | El trozo correcto existe pero no aparece en el top-5 |
| **Ranking** | Aparece en el top-5, pero no el primero, y el modelo usó otro |
| **Prompt / generación** | El contexto era bueno y la respuesta no lo usó bien |
| **Juez** | La respuesta es buena y el juez se equivocó |
| **Dataset** | La pregunta o la respuesta esperada estaban mal escritas |

El documento debe tener una tabla con `id`, pregunta, causa y una nota de una línea, y al final
un recuento por causa. Ese recuento es lo que justifica la v0.3: si la mayoría de fallos son
de *Recuperación* en preguntas `exact_term`, ya tienes el argumento para BM25.

Si descubres errores en el **dataset**, corrígelos, anótalo en el CHANGELOG y vuelve a ejecutar

| Añadir un archivo olvidado al último commit (sin push aún) | `git add archivo` y `git commit --amend --no-edit` |
| Guardar cambios a medias para cambiar de rama | `git stash` y luego `git stash pop` |
| Saber en qué rama estoy | `git branch --show-current` |

**No uses** `git push --force` ni `git reset --hard` sin entender qué hacen: pueden borrar
trabajo. Si te ves en un lío, para y pide ayuda antes.

## Anexo B. Problemas habituales

| Síntoma | Causa probable | Solución |
|---|---|---|
| `ModuleNotFoundError: No module named 'rag'` | Ejecutas fuera del entorno | Usa `uv run ...` desde la raíz |
| Error de conexión al usar tiktoken | Primera descarga del vocabulario | Ejecútalo con internet normal una vez |
| El primer `ingest` tarda mucho | Descarga del modelo de embeddings | Normal la primera vez |
| `PermissionError` al guardar el índice | Archivo abierto (por ejemplo en DB Browser) | Cierra el programa y repite |
| `index is out of sync` | Índice a medias o editado a mano | Borra `index\*` (salvo `.gitkeep`) y repite `ingest` |
| `authentication_error` de Anthropic | Clave mal copiada o sin `.env` | Revisa el `.env` en la raíz, sin comillas |
| Las métricas no cambian entre ejecuciones | El índice no se reconstruyó | Revisa la detección de cambios del paso 7 |
| `.env` aparece en `git status` | `.gitignore` roto o renombrado | No hagas `git add`; revisa el `.gitignore` |

## Anexo C. Cómo pedir ayuda a Claude

El `CLAUDE.md` de la raíz le explica a Claude Code el proyecto y le pide que te ayude **sin
escribir por ti** las funciones que estás aprendiendo. Formas útiles de usarlo:
